# ADR-0001 PNG编码升级中的成品身份与复用边界

状态：已决定（本次仅交付决策与证据，不替换既有原件，不改动运行代码）
日期：2026-11-19
证据：docs/adr-0001-experiments.md（全部数字可由 scripts/encoding-lab/run.py 复现）

## 背景

棱版计划更换PNG压缩器（stdlib `png.Encode` 默认压缩 → 更高压缩级别，实测同像素字节 −21.5%～−31.1%），并希望"对等像素结果复用计算和空间"。硬约束：旧ETag和已接受校样必须仍返回原始字节。

现行身份模型（本次决策的出发点）：

- 成品身份键含字节摘要：`id = sha256(plate:revision:scene_digest:format:sha256(bytes))`（internal/service/service.go:135-137，实验已按公式复核3/3一致）。ETag即字节摘要（internal/transport/http.go:182-189），If-None-Match精确匹配返回304。
- 校样引用成品id；accepted校样钉住成品，撤销返回409（internal/service/service.go:186-201）。
- 每次Open重放 `Hash(Data)==Digest` 校验（internal/repository/repository.go:110-114）：任何字节替换在启动时失败关闭。
- 成品字节内联在单一JSON快照（base64，×4/3）；容量256对象/128MiB，对象计数含已撤销（单调只增）；每次提交全量重写快照。
- 提交路径先栅格化后查键（internal/service/service.go:109-152）：今天连字节相同的重复渲染也不省计算（实测重复渲染47.6/47.3/48.0ms，无加速）。

## 沿四条实际路径的方案比较

### 路径一：编码

压缩器只改最终字节序列化，像素在上游已定型（internal/raster/raster.go:54-56）。当前快照不记录每个成品由哪个编码器产生——任何方案都应补一个可加的 `encoder` 字段（JSON加字段向后兼容，旧行缺省即可）。

### 路径二：成品提交

- **方案A 每种编码各自持有原件**（现状延伸，零代码）：压缩器升级后，同一稿本重渲染产生新键新对象。实测3/3等像素重渲染全部铸新对象：对象3→6，快照24,391→39,440字节（+61.7%，零新视觉信息）；256对象上限被加速消耗（128次重渲染即耗尽）；计算零复用（192×144约47ms、512×512约378ms每次重渲染）。旧引用完好（字节/ETag/304/校样钉全部保持）。另外，walkthrough的png/artifact/restore/bundle四个流程都断言"重渲染摘要不变"，无去重时3/3会失败——现有验证契约本身就把字节确定性当作不变量。
- **方案B 按视觉结果折叠身份**：存储最省，但按定义要丢弃或重指旧字节——实测模型下全部旧id/ETag与被accepted校样钉住的字节悬空（本实验中为3个成品+1条校样，占既有引用100%）。且"视觉"若带任何容差，会吞掉渲染器可观测的差别：低透明隐藏颜色改动（α=0.004，红→蓝）产生2048个差异像素、单通道最大差255，在容差≥2的视觉比较下为0。作为身份基础被拒绝。
- **方案C 提交时按精确像素去重**（推荐，见决策）：身份键不变；渲染前查（plate, revision, scene_digest, format）的available索引，命中即返回既有成品——渲染器确定性保证同稿本同像素，任何重编码都是同一视觉事实。等像素重渲染零新对象、零新字节、零栅格计算；旧引用构造性不受影响；walkthrough确定性断言保持绿色。
- **方案D 内容寻址blob分层**（后续可选）：字节迁入按摘要寻址的blob表，成品行变为元数据+引用；另加编码变体索引。相比A/C，它让"给旧场景补发新编码字节"成为可能且便宜（见路径四），但需要v1→v2单向快照迁移。

### 路径三：校样保护

accepted校样→成品id→字节摘要是一条钉死的链。A/C/D都保持逐对象身份，链不断；B把校样重指到折叠身份，被接受的字节事实消失。实测：升级前后对proof钉住的成品DELETE均返回409，该不变量在A/C/D下不依赖任何新机制即成立。

### 路径四：离线重渲染

三条真实子路径：
1. 重启恢复：state.json重放+Check；A/C/D下旧字节原样可服务（实测重启前后字节一致）。
2. 封包导出/导入：封包只含稿本；导入后重渲染在升级编码器下产生新id（实测与源成品id/摘要均不同）但像素完全一致——跨系统的等价性只能用像素哈希证明，身份本来就不可移植。
3. 刻意给旧场景换新编码：实测"解码保留原件→按新压缩器重编码"与"新编码器原生重渲染"字节完全一致（4/4，含512×512），且512×512下转码37.6ms对比重渲染约378ms（约10倍），不占用2个计算名额。**保留的原始字节就是像素真值来源，永远不需要独立像素库。**

## 实验证据摘要

完整数据与复现见 docs/adr-0001-experiments.md。关键数字（go1.24.10 linux/arm64）：

| 事实 | 实测 |
|---|---|
| 等像素异编码 | 3/3重渲染像素完全一致（精确RGBA差0），字节−21.5%；512×512为−31.1% |
| 升级后旧引用读取 | 3/3字节一致、ETag一致、304有效、校样钉409保持 |
| 方案A放大 | 对象3→6；快照+61.7%；对象上限128次重渲染耗尽 |
| 局部真实变化 | 隐藏颜色2048px/Δ255、1px镂空16px均被精确像素键区分；视觉容差≥2时隐藏颜色被吞为0 |
| 折叠安全边界 | α=0隐藏颜色、0.01px亚采样移动本就被渲染器归一化（0差），折叠不损失任何消费者可观测事实 |
| 转码等价 | 解码+重编码==原生重渲染字节，4/4完全一致；512×512节省约10倍且不占计算名额 |
| 去重启动代价 | 派生索引重建约1.0ms/成品（192×144）～8.4ms（512×512），256对象上限内一次性约0.26～2.2s |

## 决策

1. **成品身份保持字节内容寻址，永不改键、永不重指。** 既有成品id、ETag、校样引用、撤销状态原样保留；方案B（按视觉结果折叠身份）被拒绝。
2. **压缩器升级与"提交时精确像素去重"（方案C）一同上线**：渲染提交前先查（plate, revision, scene_digest, format）的available派生索引，命中即返回既有成品，不栅格化、不编码、不铸新对象。索引在Open时由保留字节解码重建（派生事实，可随时重建），无需快照迁移。去重仅限同稿本且available：撤销语义保持按对象字节级不变，不随像素等价传播。
3. **新成品增加可加字段记录编码器版本与像素哈希**（`encoder`、`pixel_hash`；旧行缺省）。像素哈希取精确RGBA（量化后8bit通道），这是允许折叠的最细粒度；任何更粗的"视觉"键（合成后比较、带容差）都会吞掉渲染器可观测差别，禁止使用。加字段的同时递进快照Schema版本号，使旧二进制对新快照失败关闭（拒绝Open）——否则旧写路径的克隆-重写会静默丢弃新字段。
4. **方案D作为后续触发式选项**：仅当需要给存量场景刻意补发新编码字节时，做v1→v2单向迁移（blob表+变体索引），迁移用既有Check同款摘要校验逐对象验证；转码路径已证字节级等价，不需要重渲染、不需要独立像素库。对象上限在D物化变体时仍按对象增长，与A相同。
5. **本次不替换既有原件**：不迁移、不重编码、不删除任何已持久化字节；上述2、3为随压缩器升级一同实施的代码变更建议，本交付只定边界。

## 事实边界：可共享 vs 必须独立保留

可共享（派生、可重建、可去重）：
- 字节blob：按摘要内容寻址，跨成品/编码/版面共享同一物理副本。
- 像素哈希（精确RGBA）：等价判定与索引键；可由任一保留字节无损解码重建。
- 场景→像素、像素→编码变体两张索引：纯派生缓存；渲染器（非压缩器）变更即作废重建。

必须独立保留（每对象权威事实，折叠即丢失）：
- 成品id↔字节绑定（ETag）：每个已签发id永远解析到原始字节。
- 成品生命周期状态：撤销按对象生效，不向等像素对象传播。
- 校样记录及其成品引用与裁决：校样针对具体字节摘要作出。
- 稿本谱系摘要链：内容寻址、不可改写。
- 每个成品字节的编码器版本归属：未来迁移判定等价类的依据。

## 影响与后续

- 行为变化仅一处：升级后对已available的（稿本,格式）重渲染返回升级前字节。需要新编码字节的场景走新稿本，或等方案D的显式变体路径。这正是"等像素结果复用计算和空间"的语义。
- 渲染器变更（非压缩器）在方案C下不会改变既有场景的像素事实——既有成品保持权威；刻意的重渲染验证属方案D路径，用像素哈希报告漂移。
- 256对象上限单调只增（含已撤销）是独立既有问题，方案C消除了升级驱动的增长，但容量规划本身需另行评审，不在本决策范围。
- SVG不涉及压缩器，字节确定性已成立，全程不受影响。
